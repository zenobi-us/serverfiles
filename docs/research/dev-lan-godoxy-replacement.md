# GoDoxy fit for dev-lan replacement

**Purpose:** Help the serverfiles maintainer decide whether GoDoxy can replace the dev-lan Caddy proxy and custom dashboard, and identify what must be verified before deployment.

**Reader:** serverfiles maintainers planning the dev-lan deployment.

**Research date:** 2026-10-12

**Scope:** This report compares official GoDoxy implementation docs and first-party GoDoxy and Podman docs with the current repository files. It does not change deployment files or establish a working deployment.

## Overview

GoDoxy is a plausible single-container replacement for Caddy plus the dashboard's service-list view: its embedded WebUI exposes routes, servers, logs, metrics, and uptime; it discovers Podman containers and can define routes with labels or YAML files. Its official Compose example requires host networking and connects to a Docker-compatible API through a socket-proxy. Podman provides that API, and Quadlet can manage containers through systemd. These facts establish a viable design direction, not a proven dev-lan deployment. [GoDoxy README](https://raw.githubusercontent.com/yusing/godoxy/main/README.md), [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml), [Podman API service manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html), [Podman Quadlet manual](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html)

GoDoxy does not demonstrate compatibility with Caddy labels, and its WebUI does not establish parity with the dashboard's custom hourly request chart or per-service resource figures. The dashboard's current figures are explicitly simulated, not live operational data. The existing rootful Podman socket is highly privileged even when mounted read-only; moving that socket to GoDoxy or its socket-proxy retains a high-impact trust boundary. [Dashboard README](../../systems/dev-lan/definitions/dashboard/README.md), [dashboard data functions](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts), [Podman API service manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html)

## Current dev-lan deployment

The current Quadlet runs `docker.io/lucaslorentz/caddy-docker-proxy:2.12-alpine`, joins `shared.network`, publishes ports 80 and 443 (TCP and UDP), and mounts `/run/podman/podman.sock` at `/var/run/docker.sock` with `:ro`. It selects the `shared` ingress network and enables Caddy's no-scope option. It stores Caddy data and config under `/var/lib/caddy/`. [Current Caddy Quadlet](../../systems/dev-lan/quadlets/caddy.container)

The dashboard is a TanStack Start app. Its README and design state that its inventory and telemetry are illustrative, and that it does not discover services, verify DNS or health, or read live logs. The server functions return four fixed sample services plus deterministic hourly request, error, log, CPU, memory, and storage values. [Dashboard README](../../systems/dev-lan/definitions/dashboard/README.md), [dashboard design](../../systems/dev-lan/definitions/dashboard/DESIGN.md), [dashboard data functions](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts)

That makes GoDoxy's built-in homepage a possible replacement for the custom app as an operator-facing inventory, but it is not a literal replacement of live application behavior: today's charts and records are mock data. GoDoxy's docs describe homepage display names, icons, categories, descriptions, and URLs; they do not claim to import this dashboard's TypeScript data or layout. [GoDoxy WebUI customization docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/customization/WebUI.mdx), [dashboard design](../../systems/dev-lan/definitions/dashboard/DESIGN.md)

## Runtime, socket access, and privileges

GoDoxy documents support for discovering Docker and Podman containers. Its Compose sample defaults `DOCKER_SOCKET` to `/var/run/docker.sock`; its generated environment docs say to set this path to `/var/run/podman/podman.sock` for Podman. Podman's rootful socket is `/run/podman/podman.sock`, and its API includes a Docker v1.40 compatibility layer. GoDoxy's Docker client negotiates an API version. These sources confirm the intended protocol path, but do not prove every GoDoxy API call works against the repository's Podman version. [GoDoxy README](https://raw.githubusercontent.com/yusing/godoxy/main/README.md), [GoDoxy environment example](https://raw.githubusercontent.com/yusing/godoxy/main/.env.example), [GoDoxy Docker client](https://raw.githubusercontent.com/yusing/godoxy/main/internal/docker/client.go), [Podman API service manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html)

GoDoxy's reference Compose deployment uses `ghcr.io/yusing/socket-proxy`, enables container, event, info, ping, version, and POST access, and explicitly enables start, stop, and restart operations. GoDoxy then connects to that proxy through `GODOXY_DOCKER_HOST`. The example therefore does not present a read-only discovery policy. The exact least-privilege filter needed for dev-lan, and whether GoDoxy works with lifecycle operations disabled, are unverified. [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml), [GoDoxy environment example](https://raw.githubusercontent.com/yusing/godoxy/main/.env.example)

Podman warns that its API grants full access to Podman and permits arbitrary code execution as the API service user. The socket uses Unix file permissions as its primary access control. The current `:ro` mount does not change what requests the API authorizes; it only marks the mounted filesystem path read-only. Do not treat a read-only socket mount as a privilege boundary. An API client with rootful socket access remains a root-level control risk. [Podman API service manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html), [current Caddy Quadlet](../../systems/dev-lan/quadlets/caddy.container)

Podman documents separate rootful and rootless endpoints: `/run/podman/podman.sock` for rootful Podman and `$XDG_RUNTIME_DIR/podman/podman.sock` for rootless Podman. The existing Caddy Quadlet consumes the rootful endpoint. GoDoxy must use that same endpoint to discover the current rootful containers; switching to a rootless endpoint would expose a different container set. Podman also requires `label=disable` when a container accesses its API socket. How to express the needed SELinux setting safely in the final Quadlet is not validated here. [Podman API service manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html), [current Caddy Quadlet](../../systems/dev-lan/quadlets/caddy.container)

## Network and route compatibility

GoDoxy's official README says to run its main container in host network mode and not to change that mode. The current Caddy container instead joins `shared.network`. GoDoxy's deployment would therefore have a different network boundary and would bind host listeners directly; port publication settings from the current Quadlet cannot simply be copied unchanged. Host mode aligns with using host ports 80 and 443, but exact bind addresses, HTTP/3/UDP exposure, and conflict behavior on this machine remain to be tested. [GoDoxy README](https://raw.githubusercontent.com/yusing/godoxy/main/README.md), [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml), [current Caddy Quadlet](../../systems/dev-lan/quadlets/caddy.container)

GoDoxy can derive an upstream address from the selected Podman network's container IP. Its implementation uses the named network when configured, otherwise it chooses the first network with an IP. It reports an error if a configured network is absent. A host-networked GoDoxy can still read a target container's network metadata through the API, but the sources do not prove that GoDoxy's host-network namespace can reach every `shared`-network address in this host's firewall and Podman setup. That path needs a local connectivity test. [GoDoxy container address selection](https://raw.githubusercontent.com/yusing/godoxy/main/internal/docker/container.go), [Podman network manual](https://docs.podman.io/en/latest/markdown/podman-network.1.html)

GoDoxy routes can come from `proxy.*` container labels or YAML route files. Its `proxy.aliases` accepts short aliases or FQDNs; the route docs support explicit FQDN aliases and route-level host, port, scheme, and homepage settings. `.dev.lan` FQDN aliases are syntactically compatible with GoDoxy's documented matching model. The actual DNS records, upstream targets, and current labels for apps outside this machine definition were not available in the inspected dev-lan files. [GoDoxy route docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Configuring-Routes.mdx), [GoDoxy domain matching docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/advanced-topics/Domain-Matching.mdx), [dashboard sample data](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts)

Caddy's `caddy.*` labels and GoDoxy's `proxy.*` labels are different configuration contracts. GoDoxy does not document Caddy-label import. Each existing proxy label must be inventoried and translated, or replaced with Git-managed GoDoxy route YAML. GoDoxy file routes support non-container upstreams and can represent additional aliases, which matches the shape of sample aliases and version hostnames in the dashboard. It remains unverified whether the sample names correspond to deployed services or valid upstream endpoints. [GoDoxy route docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Configuring-Routes.mdx), [GoDoxy provider implementation notes](https://raw.githubusercontent.com/yusing/godoxy/main/internal/route/provider/README.md), [dashboard sample data](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts)

## WebUI, logs, metrics, and authentication

GoDoxy describes its WebUI as managing routes, config, containers, logs, metrics, and uptime. Its homepage configuration supports route presentation fields such as display name, icon, URL, category, and description. These functions overlap the custom dashboard's service tree and service detail summary. Its README also describes monitoring host CPU, disk, and memory plus Docker logs. The source docs do not establish feature parity with the dashboard's hourly per-service request counts, error counts, request-path table, or per-container resource limits. Treat that parity as unverified; do not represent GoDoxy's generic logs and metrics claims as the dashboard's exact telemetry. [GoDoxy README](https://raw.githubusercontent.com/yusing/godoxy/main/README.md), [GoDoxy WebUI customization docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/customization/WebUI.mdx), [dashboard data functions](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts)

GoDoxy docs describe configurable HTTP access logs with file or standard-output destinations, format, field filtering, and retention. Its ACL docs also describe access logging. That supports real proxy-request logging when configured; it does not confirm a built-in per-service interactive request timeline identical to the mock dashboard. The current dashboard's request log entries are generated sample records. [GoDoxy access-control and access-logging docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/advanced-topics/Access-Control.mdx), [GoDoxy configuration example](https://raw.githubusercontent.com/yusing/godoxy/main/config.example.yml), [dashboard data functions](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts)

GoDoxy documents username/password credentials and OpenID Connect (OIDC) for WebUI access. It also documents per-route OIDC middleware, IP/CIDR access controls, and optional country/timezone controls that require MaxMind data. The generated environment documentation warns that disabling authentication is for development only, and that its optional unauthenticated local API exposes unrestricted access if bound beyond loopback. The deployment must set and protect credentials and keep the unauthenticated API disabled or loopback-only. [GoDoxy environment docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Environment-Variables.mdx), [GoDoxy OIDC docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/OIDC.mdx), [GoDoxy access-control docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/advanced-topics/Access-Control.mdx)

## TLS, persistence, and updates

GoDoxy supports a local certificate/key pair or automatic ACME certificates through DNS-01 providers. The examples mount `/app/certs` for certificates and agent TLS client certificates, `/app/data` for data, `/app/logs` for logs, and `/app/config` for configuration. Its default shared HTTPS listener is port 443 and its default HTTP listener is port 80. Local `.dev.lan` names are not necessarily publicly issued names, so certificate issuer, trust chain, and client trust for this LAN are deployment decisions, not confirmed facts. The final config must decide between an existing trusted certificate, an internal ACME authority, or another supported certificate path. [GoDoxy certificate docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/advanced-topics/Certificates.mdx), [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml), [GoDoxy environment docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Environment-Variables.mdx)

The existing proxy persists Caddy data and config under `/var/lib/caddy/data` and `/var/lib/caddy/config`. GoDoxy's example uses separate config, logs, data, and certs directories. A migration must preserve or intentionally replace certificate material and configuration; the two products' on-disk formats are not interchangeable. GoDoxy also permits WebUI edits that override label and route-file settings. For Git as the desired-state boundary, prefer repository-managed config and route files, and define whether WebUI writes are permitted. The exact persistence behavior of every mutable GoDoxy file has not been independently verified. [current Caddy Quadlet](../../systems/dev-lan/quadlets/caddy.container), [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml), [GoDoxy WebUI docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/customization/WebUI.mdx)

The official Compose example defaults `TAG=latest`; the basics docs also list version tags. The GoDoxy README links GitHub releases, but the inspected docs do not give a Quadlet-specific auto-update or rollback policy. A reproducible systemd deployment should choose a reviewed version tag or image digest and define how upgrades and rollback occur. Whether the currently targeted release works with dev-lan's Podman build and API is unverified. [GoDoxy environment example](https://raw.githubusercontent.com/yusing/godoxy/main/.env.example), [GoDoxy basics docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Basics.mdx), [GoDoxy releases](https://github.com/yusing/godoxy/releases)

## Quadlet and systemd feasibility

Podman documents `.container` Quadlet units, support for system and user systemd managers, `[Unit]` dependencies, restart settings, and `[Install]` behavior. This proves that a containerized GoDoxy process can be managed by Quadlet in principle. GoDoxy's official setup instructions and published deployment example use Docker Compose, not Quadlet; no official GoDoxy Quadlet unit or tested systemd recipe was found. Therefore, Quadlet deployment is technically plausible but is not an officially documented GoDoxy install path. [Podman Quadlet manual](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), [GoDoxy setup docs](https://demo.godoxy.dev/docs/godoxy/Setup), [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml)

The main container can use `Network=host`, image, environment values, mounts, and systemd restart policy in a `.container` Quadlet; Quadlet supports corresponding container options. The socket-proxy's listener and port setup need a separate compatible Quadlet design. Do not assume the Compose `ports` entry maps directly to GoDoxy's host-network process or that a particular socket-proxy image supports a proposed environment interface without checking its own source. The main-image unit, SELinux access, listener binds, dependency ordering, and filesystem ownership remain to be proven on dev-lan. [Podman Quadlet manual](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), [GoDoxy Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml), [GoDoxy setup docs](https://demo.godoxy.dev/docs/godoxy/Setup)

| Requirement | Evidence and assessment |
| --- | --- |
| Replace Caddy ingress | **Likely fit.** GoDoxy is a reverse proxy with HTTP, TCP, and UDP routes and supports Podman discovery. Host networking differs from the current `shared` network; verify app network reachability and listeners. [README](https://raw.githubusercontent.com/yusing/godoxy/main/README.md), [GoDoxy container source](https://raw.githubusercontent.com/yusing/godoxy/main/internal/docker/container.go) |
| Replace custom service directory | **Partial fit.** The embedded homepage can display discovered routes with names and categories. It is not the same dashboard implementation, and no import or layout parity is documented. [WebUI docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/customization/WebUI.mdx), [dashboard design](../../systems/dev-lan/definitions/dashboard/DESIGN.md) |
| Show useful real telemetry | **Unverified parity.** GoDoxy documents logs, metrics, and uptime, while current dashboard data is simulated. Confirm the exact per-container metrics and per-route request-history UI before removing the custom dashboard. [README](https://raw.githubusercontent.com/yusing/godoxy/main/README.md), [dashboard functions](../../systems/dev-lan/definitions/dashboard/src/server/functions.ts) |
| Connect to current Podman | **Protocol supported; integration unverified.** Podman exposes Docker API v1.40 compatibility at its rootful socket and GoDoxy documents Podman support. Test API calls and event watching against the host's Podman version. [Podman API manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html), [GoDoxy Docker client](https://raw.githubusercontent.com/yusing/godoxy/main/internal/docker/client.go) |
| Keep least privilege | **Needs security decision.** The rootful API grants full Podman control. The official socket-proxy example allows lifecycle actions. Prove a narrower permission set or explicitly accept the expanded trust boundary. [Podman API manual](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html), [Compose example](https://raw.githubusercontent.com/yusing/godoxy/main/compose.example.yml) |
| Preserve hostnames and certificates | **Configuration fit, deployment unknown.** GoDoxy accepts FQDN aliases and local certificates, but current DNS and client trust for `.dev.lan` were not verified. Translate the existing labels and choose a certificate trust model. [route docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Configuring-Routes.mdx), [certificate docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/advanced-topics/Certificates.mdx) |
| Use systemd/Quadlet | **Plausible, not official GoDoxy deployment guidance.** Podman supports Quadlet containers; GoDoxy publishes a Compose setup only in the sources inspected. Test both main app and socket proxy as generated systemd services. [Quadlet manual](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), [GoDoxy setup](https://demo.godoxy.dev/docs/godoxy/Setup) |
| Keep desired state in Git | **Possible with qualification.** YAML routes and config are supported, but WebUI changes can override route files and labels. Establish policy and persistence for mutable state. [route docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/getting-started/Configuring-Routes.mdx), [WebUI docs](https://raw.githubusercontent.com/yusing/godoxy-wiki/main/content/docs/godoxy/customization/WebUI.mdx) |

Before a deployment change, verify these points on the target machine:

- **API behavior:** Test GoDoxy discovery, labels, network inspection, events, container logs, and shutdown behavior against the exact rootful Podman release.
- **Socket policy:** Determine which socket-proxy API routes and methods GoDoxy requires. Test that discovery still works with lifecycle methods denied. Keep the listener private.
- **Network reachability:** Confirm the host-networked GoDoxy process can reach each target container's `shared` network IP and required port.
- **Route migration:** Inventory actual Caddy labels and hostnames, translate them to GoDoxy labels or checked-in route files, and confirm DNS behavior for `.dev.lan` aliases.
- **TLS and auth:** Select certificate issuance and client trust. Configure WebUI auth, secure cookies, secret handling, and the API listener.
- **Dashboard parity:** Inspect GoDoxy's live UI for per-service resource metrics and request history. Decide whether missing custom behavior is acceptable before deleting the app.
- **Quadlet lifecycle:** Validate generated unit dependencies, SELinux policy, bind addresses, user/group ownership, restart behavior, image pin, upgrades, and rollback.
